# GitLab CI/CD Modular Structure

This document explains the refactored modular structure of the GitLab CI/CD pipeline.

## Overview

The original `.gitlab-ci.yml` file (1721 lines) has been split into multiple focused files for better maintainability, readability, and organization. Each file handles a specific aspect of the pipeline.

## File Structure

```
.gitlab-ci.yml                    # Main entry point (45 lines)
├── .gitlab-ci-vars.yml           # Global variables (52 lines)
├── .gitlab-ci-terraform.yml      # Terraform infrastructure jobs (656 lines)
├── .gitlab-ci-docker.yml         # Docker build jobs (226 lines)
├── .gitlab-ci-validate.yml       # Validation jobs (130 lines)
├── .gitlab-ci-test.yml           # Test jobs (44 lines)
├── .gitlab-ci-package.yml        # Package jobs (43 lines)
└── .gitlab-ci-deploy.yml         # Deployment jobs (630 lines)
```

## File Descriptions

### `.gitlab-ci.yml` (Main Entry Point)
**Purpose**: Orchestrates all modular components using GitLab's `include` directive.

**Contents**:
- Workflow rules to prevent duplicate pipelines
- Include directives for all modular files
- Pipeline stage definitions

**Lines**: 45 (down from 1721)

---

### `.gitlab-ci-vars.yml`
**Purpose**: Defines all global variables used across the pipeline.

**Contents**:
- Docker registry configuration
- Terraform configuration
- Yandex Cloud variables
- GitLab authentication variables
- Application configuration
- Build optimization settings

**Lines**: 52

---

### `.gitlab-ci-terraform.yml`
**Purpose**: Handles all Terraform infrastructure provisioning jobs.

**Jobs Included**:
- `terraform:fmt` - Format checking
- `terraform:validate` - Configuration validation
- `terraform:security-scan` - Security scanning with tfsec
- `terraform:plan:staging` - Staging plan creation
- `terraform:plan:production` - Production plan creation
- `terraform:apply:staging` - Staging infrastructure deployment
- `terraform:apply:production` - Production infrastructure deployment
- `k8s:update-kubeconfig` - Kubernetes configuration update
- `terraform:destroy:staging` - Staging teardown
- `terraform:destroy:production` - Production teardown

**Lines**: 656

**Key Features**:
- GitLab HTTP backend authentication with PAT support
- Multi-environment support (staging/production)
- HTTP 409 lock release error handling
- Artifact generation for downstream jobs

---

### `.gitlab-ci-docker.yml`
**Purpose**: Manages Docker image building and registry operations.

**Jobs Included**:
- `build:backend` - Multi-arch backend Docker build
- `build:frontend` - Multi-arch frontend Docker build
- `cleanup:registry` - Registry cleanup for old images

**Lines**: 226

**Key Features**:
- Multi-architecture support (linux/amd64, linux/arm64)
- BuildKit cache optimization
- Idempotent builds with image existence checks
- Retry mechanisms for registry operations
- Automatic cleanup of old images

---

### `.gitlab-ci-validate.yml`
**Purpose**: Runs validation and linting jobs.

**Jobs Included**:
- `validate:syntax` - YAML and shell script linting
- `validate:docker` - Dockerfile linting with hadolint
- `helm:lint` - Helm chart validation

**Lines**: 130

**Key Features**:
- yamllint with custom line-length configuration
- Cross-platform tool installation (Alpine, macOS)
- Non-blocking validation for optional checks

---

### `.gitlab-ci-test.yml`
**Purpose**: Executes automated tests for backend and frontend.

**Jobs Included**:
- `test:backend` - Maven-based Spring Boot tests
- `test:frontend` - Jest-based React tests with coverage

**Lines**: 44

**Key Features**:
- PostgreSQL service integration for backend tests
- Coverage reporting (Cobertura format)
- Caching for Maven dependencies and npm modules
- JUnit test report artifacts

---

### `.gitlab-ci-package.yml`
**Purpose**: Creates deployment artifacts.

**Jobs Included**:
- `package:compose` - Docker Compose deployment package

**Lines**: 43

**Key Features**:
- Environment variable substitution with envsubst
- Artifact generation for downstream deployments
- Docker registry image tag injection

---

### `.gitlab-ci-deploy.yml`
**Purpose**: Handles all deployment operations to Yandex Cloud VM and Kubernetes.

**Jobs Included**:
- `deploy:staging` - Yandex Cloud VM staging deployment
- `deploy:production` - Yandex Cloud VM production deployment
- `deploy:k8s:staging` - Kubernetes staging deployment with Helm
- `deploy:k8s:production` - Kubernetes production deployment with Helm
- `deploy:patch-ingress-externalip` - Ingress controller IP patching
- `deploy:probe-root` - Post-deployment health checks

**Lines**: 630

**Key Features**:
- Multiple deployment targets (VM, Kubernetes)
- Helm-based Kubernetes deployments
- Ingress configuration and health checks
- External IP auto-detection and patching
- Post-deployment verification with curl probes

## Benefits of Modular Structure

### 1. **Improved Readability**
- Each file focuses on a single concern
- Smaller file sizes (43-656 lines vs. 1721 lines)
- Clear naming conventions indicate file purpose

### 2. **Better Maintainability**
- Easier to locate specific job configurations
- Changes are isolated to relevant files
- Reduced merge conflicts in team environments

### 3. **Enhanced Reusability**
- Templates and anchors can be shared across files
- Easy to include/exclude specific components
- Modular design supports future extensions

### 4. **Simplified Testing**
- Individual files can be validated independently
- Easier to test specific pipeline stages
- Faster iteration on changes

### 5. **Clear Separation of Concerns**
- Variables separated from job definitions
- Infrastructure jobs isolated from application jobs
- Validation separated from deployment

## Migration Notes

### Backward Compatibility
- Original `.gitlab-ci.yml` backed up as `.gitlab-ci.yml.backup`
- All jobs and stages preserved exactly as in original
- No functional changes to pipeline behavior

### GitLab CI/CD Behavior
- GitLab automatically merges included files at runtime
- Pipeline visualization remains the same
- Job dependencies and needs unchanged
- Environment and artifact handling preserved

## Usage

### Modifying Jobs
1. Navigate to the relevant file based on job type
2. Edit job configuration as needed
3. Commit changes (GitLab will automatically pick up the modification)

### Adding New Jobs
1. Identify the appropriate file for the job type
2. Add job configuration following existing patterns
3. Update stage definitions in main `.gitlab-ci.yml` if new stage needed

### Disabling Components
Comment out or remove the `include` directive in `.gitlab-ci.yml`:
```yaml
include:
  # - local: '.gitlab-ci-terraform.yml'  # Disabled
  - local: '.gitlab-ci-docker.yml'
```

## Stage Order

The pipeline stages execute in this order:
1. **validate** - Syntax and configuration validation
2. **plan** - Terraform plan creation
3. **build** - Docker image building
4. **test** - Automated testing
5. **package** - Deployment artifact creation
6. **deploy** - Application deployment

## Conclusion

This modular structure provides a clean, maintainable, and scalable approach to CI/CD configuration. Each file can be understood and modified independently, making the pipeline easier to work with for teams of all sizes.
